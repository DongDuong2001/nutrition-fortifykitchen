# cc-68: never lose a write, yesterday editable, one diary on every device

Branch `feat/ui-cc-68` (cc-67 and main with cc-63 merged in). Web only: nothing under `apps/api`, the database, migrations or deploy. sw.js VERSION `2026-10-19.11`, release `2026-10-19b` (above cc-67's `2026-10-19a`).

Product rule: today AND yesterday (Asia/Ho_Chi_Minh) are editable, two or more days back are read-only, behind one constant (`EDITABLE_PAST_DAYS = 1`, `lib/day-rules.ts`). Demo and mock keep the past read-only.

## Part 1: never lose a write
- **Write-ahead outbox in IndexedDB** (`lib/outbox.ts`, `lib/idb.ts`): one record per write, committed before the request leaves. A page killed during a fetch finds the write on disk and sends it again (the id is the client's, so it is idempotent). Today's list and the outbox no longer go through the deferred writer (`lib/deferred-write.ts` is deleted); every write of the diary lands in localStorage at once.
- **Storage errors are never swallowed.** A quota or blocked-storage error raises a lasting notice "Máy hết chỗ lưu, mục vừa ghi chưa được lưu" (`components/sync/sync-alerts.tsx`) and a `storage` report to /client-errors.
- **Add/delete race:** an add that was ever attempted keeps going and the DELETE queues behind it (per-entry order).
- **Profile, weight, favourites, training** go through the same outbox (last write wins). A server profile on load never overwrites a newer unsynced local change.
- **The day is chosen when the request is sent** (`getTodayIsoVN()`), so an offline add made before midnight lands on the day it was made. `navigator.storage.persist()` is asked after sign-in.
- The engine (`lib/sync-engine.ts`) loads after first paint; `lib/api-client.ts` stays a thin front.

## Part 2: yesterday is editable
+ Thêm, edit, delete, move and Chép hôm qua work on yesterday like on today; two days back stays Chỉ xem. Light copy, no extra banner. While the API still answers 409 for yesterday, the write is held (Thử lại stays); a 409 for a day beyond the window is final with a lasting marker. "Có gì mới" item "Sửa được hôm qua" and a 2-step tour (the arrow that opens yesterday, + Thêm).

## Part 3: one diary on every device
- **History from the server**: `GET /days?from=&to=` when it answers (`{ days: [...] }`, every date of the range; asked in windows of at most 90 days, the server's limit is 100), else `GET /days/{date}` one by one. Cached as one slim record per day in IndexedDB (400-day prune). The old localStorage archive is moved over without loss; entries the server never confirmed are sent again.
- **Account guard (X1):** a storage event on the email key plus `onAuthStateChange`; on a mismatch the page drops its state and reloads to the gate; the account is compared before each outbox batch.
- **Tabs:** one drainer at a time (Web Lock `h1t-outbox-drain`), the others hear it through BroadcastChannel.
- **Đăng xuất (X8):** with nothing waiting, the account's local data is wiped; otherwise the confirm "Còn {n} mục chưa đồng bộ. Đăng xuất bây giờ sẽ xóa chúng khỏi máy này." with "Đồng bộ rồi đăng xuất" (default) and "Vẫn đăng xuất". cc-63's cookie clear runs first (inside `signOut()`), then the wipe. Legacy unscoped keys are deleted, never adopted by whoever signs in next.

## Part 4: retries and visibility
- Per-item exponential backoff with jitter, `Retry-After` honoured, parked after 8 tries with Thử lại. Focus, tab shown and `online` send at once; only the 60 s poll respects the backoff.
- Two 401s after the session renewal: the lasting banner "Phiên đăng nhập hết hạn · Đăng nhập lại".
- One sync status in every header (Ngoại tuyến, Đang lưu…, Chưa lưu (n), Đã lưu); a tap opens the list with Thử lại. `outbox_age` and `storage` reports.
- A service-worker update never reloads while the outbox is non-empty or a write is sending ("Có bản mới" waits). Android Background Sync drains the IndexedDB outbox from `sw.js` (it only removes what the server accepted; iOS has none).
- cc-63's rule is applied to the engine: the server's text is never kept, shown or sent; a held write keeps its status, a report carries the status and the error code only.

## Part 5: no lag
Measured on a live-mode build of this branch (fake API, 390 x 844, `tests/probes/cc_68_perf.py`):

| | Before | After |
|---|---|---|
| React commits per refresh that finds nothing new (focus / poll path, 5 runs) | 3, 3, 3, 3, 3 | 0, 0, 0, 0, 0 |
| 3,000-food catalogue at 4x CPU, cold load (download, map, copy to IndexedDB) | 222 ms, no long task from the catalogue | 193 to 241 ms, no long task from the catalogue |
| same, warm load (read the copy) | 49 ms | 52 to 60 ms |

`mergeServerDay` hands back the entries the device already has when the server says the same, so `replaceDay` returns the same list and nothing that reads it renders; a sync that sent nothing no longer bumps `syncVersion`. The catalogue copy is kept in chunks of 125 foods (each its own request, a yield between, the record that names them written last, so a copy that did not finish is never read). Honest note: on this fake catalogue (60 nutrients a food) neither version had a long task from the catalogue itself, so the chunking is a bound, not a visible gain; the one long task in the runs is the page's own start (about 57 to 89 ms, before the load). The load is timed by a User Timing measure `h1t:catalogue`.

## Migration notes
- localStorage `h1t_offline_outbox_<account>` (and the old unscoped one, taken by the first account that loads) becomes one IndexedDB record per write; the localStorage key is removed only after the records are on disk. A second load changes nothing.
- localStorage `h1t_day_archive_v1_<account>` becomes `days` records in IndexedDB (database `h1t` v2: stores `kv`, `outbox`, `days`).
- The catalogue copy moves from one record to chunks; the old record is still read and replaced on the next save.
- The old unscoped outbox (`h1t_offline_outbox`) is kept for the account it was written for: the owner is noted when the browser's email changes (`lib/legacy-outbox.ts`), or is the account that loads when nobody switched. Another account that signs in first does not take it, nothing is sent for it, it stays on disk until its own account signs in, and it is reported once (`/client-errors`, kind `storage`, message `legacy_outbox_unclaimed`). With nobody to name (signed out under the old version) it stays unclaimed.
- The other old unscoped keys (entries, sample edits, recents, favourites, saved meals, archive, profile, settings, training) are deleted on load.

## What the app now uses from the API
- `POST /foods/custom` with `one_off: true` for the food of an edited dish (category `one_off`, listed nowhere). Foods made before the flag stay hidden by their id and name.
- `GET /days?from=&to=` for history, with the per-day read as the fallback.
- `/client-errors` kinds `storage` and `outbox_age`.
- Only `error.code` of an error body is read (never shown, logged or sent: cc-63); the app's own notices carry the words.
- `lib/api-client.ts` is Dong's file: its dead methods (nothing called them) were removed and the write path moved to `lib/sync-engine.ts`.
