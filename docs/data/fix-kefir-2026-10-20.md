# Kefir fix, 20/10/2026

Coach: "kefir is made from pasteurised milk, the numbers look wrong". The catalogue has two kefir rows, both named "Yogurt kefir". This keeps one, with a real source, and hides the other. Data and SQL only: the JSON is for the importer, the SQL is for Dong to run. Nothing here touches the database, migrations or server.

Files: `docs/data/fix-kefir-2026-10-20.json`, `docs/data/remove-kefir-lowfat-2026-10-20.sql`, this file.

**Order: import the JSON first (`importfoods --file`), then run the SQL.** The SQL refuses to run if the kept row is not yet named "Kefir".

## Source: what each table has

Wanted: plain kefir from whole (3 to 3.5 % fat) pasteurised milk, searched in the order NIN, Canadian Nutrient File, Fineli, NEVO.

- **NIN (Vietnam, `vn_nin`)**: no kefir. Only yogurt: NIN 10004 "Sữa chua", 10005 (skimmed), 10031, 10035, 10036 (whole-milk yogurts). Not used.
- **Canadian Nutrient File: used.** Record **6291 "Kefir, (2-3.9% M.F.)"**, read from the CNF API on 20/10/2026 (`food-nutrition.canada.ca/api/canadian-nutrient-file`, `food/?id=6291`, `nutrientamount`, `servingsize`). 34 of the nutrients the catalogue tracks are in the record, no gaps. Fat is 3.6 g, so it is a whole-milk kefir, but the record says "2-3.9 % milk fat", not "whole" or "pasteurised", and I could not see its preparation. The same table also has 6999 "Kefir, plain, low fat (0.5-1.9% M.F.)" and 7000 (fruit flavoured, low fat); neither is used.
- **Fineli (Finland)**: not read. `fineli.fi` sits behind a Cloudflare challenge ("Just a moment") for scripts, which I did not try to get around, and a web search found no Fineli kefir record.
- **NEVO (Netherlands)**: not read. A web search found no NEVO kefir record, and the online tool is a script-driven page.
- **A Vinamilk kefir**: none found. The vinamilk.com.vn home page and product search results list yogurts and Probi drinks, no kefir, so `brand` is null. If a real Vinamilk kefir product exists, it would be its own label row.

Because the CNF has a record that fits and comes before Fineli and NEVO in the order, those two were not needed.

**Portion weight, please check.** `1 ly (200 ml)` is 188.33 g because CNF's own serving table gives 200 ml = 1.88328 x 100 g, a density of 0.94 g/ml. That is lighter than water, and kefir is usually about 1.03 g/ml (200 ml would be about 206 g). I used the source's number as you asked ("density only if the source gives one"); if you prefer 200 g or 206 g, change `grams` in the JSON. The ly stays the first portion, as "200 ml" was, so the default serving does not change. "1 hộp" is gone.

## Removal plan for the other row

How foods are referenced (`migrations/`, `apps/api/internal`):

| Table | Link | Handling in the SQL |
|---|---|---|
| `diary_logs` | `food_id`, ON DELETE RESTRICT (so the row cannot be deleted while entries point at it) | `food_id` moved to the kept row |
| `user_favourites` | PK (user_id, food_id) | copied across (`ON CONFLICT DO NOTHING`), old rows deleted |
| `user_recents` | PK (user_id, food_id) | copied across; if a user has both, the later `used_at` wins; the old label "1 chén (cup)" is not a portion of the kept row, so the label is cleared (grams stay) |
| `saved_meal_items` | `food_id` | `food_id` moved; label cleared, grams stay |
| `food_portions` | CASCADE, belongs to the food | nothing to do |

No table for recipes or dish parts points at `foods(id)`: the recipe rows are foods themselves. Custom foods only store `created_by`.

**Hide, not delete.** `foods.is_archived` exists (migration 000012). The search, favourites, recents and saved-meal queries all filter on `is_archived = false`, so setting it hides the low-fat row everywhere. It is better than a delete here: the row keeps its key (usda_sr_legacy, FDC 170904), so importing an old file that still holds that record only updates the hidden row and cannot bring a second kefir back. The SQL also moves the kept row's key to `cnf` / `CNF 6291`, which the importer cannot do. The SQL ends with `ROLLBACK`; change it to `COMMIT` after reading the before and after counts it prints.

**Do old diary entries change?** No. A diary entry stores its own snapshot when it is written: `nutrients_snapshot`, `name_snapshot`, `calories`, `portion_label` and `grams` (`createEntrySQL` in `apps/api/internal/diary/repository.go`), and the diary and trends reads use those columns. Old low-fat entries keep the low-fat numbers and the name "Yogurt kefir"; only their `food_id` link moves to the kept row. New entries use the new numbers.

**Tested on a scratch database.** I ran the SQL on a throwaway local Postgres 16 (not the project database) with stub copies of the six tables, the two kefir rows and sample references, including users who had both foods as favourites and recents. Result: `ROLLBACK` left the data untouched; `COMMIT` left nothing on the old row (2 diary entries, 2 favourites, 3 recents, 1 meal item moved or merged), the kept row as `Kefir / cnf / CNF 6291`, the old row `is_archived = true`, and 1 visible kefir row. A second run refuses ("already done"), and so does a run before the JSON import. That database was deleted afterwards.

## Check before running

- `data/seed_foods.json` still has the old kefir record under usda_foundation / `food-yogurt-kefir` with the old numbers. After the SQL, nothing sits at that key any more, so re-running the seed import would create the old row again. Update or remove that record in the seed if the seed is ever re-run.
- The web demo food `food-yogurt-kefir` (`lib/mock/foods.ts`, used in demo mode only) is only looked up by its own id; I found no code that finds the live row by that `source_id` (the coach foods, dish recipes and raw/cooked pairs do not list kefir), so the key change should not affect it.
