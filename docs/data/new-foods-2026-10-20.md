# New foods, 20/10/2026

For Dong's importer. Data only: `docs/data/new-foods-2026-10-20.json` (6 rows: 5 new foods and 1 update of a live row). No migration, no API or DB change was made. Values are copied from the USDA FoodData Central CSVs in `food-research/usda` (SR Legacy 2018-04, Foundation 2026-04-30) and rounded as in `round_nutrients.py` (energy, protein, carbs, fat, fiber to 1 decimal; every other nutrient to 3 significant figures). Nothing is estimated: a nutrient the source record does not have is left out, never 0 or null. Values are per 100 g of the edible part.

The live catalogue was read on 20/10/2026 from `GET /api/v1/foods` on lehongkhanh.vn: 1,273 foods. The server caps `limit` at 500, so `limit=5000` returned 500 and the catalogue was read in 3 pages (`page=1..3`, `limit=500`).

## Updated rows

**Nho xanh (usda_sr_legacy FDC 174683) becomes "Nho xanh, nho đỏ, nho đen".** The importer upserts on `source` + `source_id`, so this row changes the live one and creates nothing new. USDA's record is "Grapes, red or green (European type, such as Thompson seedless), raw": red and green grapes are one USDA food, and the Vietnamese black grape is the same European type, so one row serves all three. The name was changed because the app's food search (`apps/web/lib/search.ts`) reads only the name (and brand) and has no alias or keywords field. It matches the query as whole words, a prefix or a substring, with or without accents, so each colour must appear in the name as "nho" + colour. Checked with the real `searchFoods` on a list holding this row, "Nho khô" and "Nho ngọt":

| Query | Finds |
|---|---|
| nho xanh, nho đỏ, nho đen | this row |
| nho do, nho den (no accents) | this row |
| Nho Đen, NHO ĐỎ (capitals) | this row |
| nho | Nho khô, Nho ngọt and this row |

A name like "Nho (xanh, đỏ, đen)" fails: "nho đỏ" and "nho đen" find nothing. "Nho xanh (nho đỏ, nho đen)" works too; the comma form is shorter.

What changes in the live row, compared with it on 20/10:

- `name_vi`: "Nho xanh" to "Nho xanh, nho đỏ, nho đen".
- Portions: "1 chùm nhỏ" (126 g) and "1 chén" (151 g) are gone, leaving "100 g" (fruit is gram-only; the same removal is in `edible-part-portions-2026-10-19.json`, so running both files is safe). The importer replaces a food's portions on every upsert.
- Nutrients: the same keys and the same source record, only rounded as the other rows are: protein 0.72 to 0.7, fat 0.16 to 0.2, sugars 15.48 to 15.5, water 80.54 to 80.5. Every other value is unchanged.
- Unchanged: `source`, `source_id`, `category` (trai_cay), `name` (the USDA description), `brand` (null), `tip_vi` (null). The API does not return brand or tip_vi; both are null in the import record that created the row (`food-research/h1t-foods-batch2.json`).

## Twins and yield

Da gà (sống) and Da gà (nướng) follow the Cánh gà (sống)/(nướng) precedent: "nướng" is a prepared state, so it is its own list row and does not join the raw one in `lib/food-twins`. Chân gà (luộc) and Bào ngư (sống) have no other state in the data, so each stays a single row, and so do the grape row and the juice (fruit and drinks never group). None of the six ids is in `raw-cooked-pairs`, so `lib/yield` goes by name and group for them.

## How Dong imports this

From `apps/api`, with `DATABASE_URL` set. Dry-run first: it parses the file and prints the completeness report, and writes nothing.

```bash
go run ./cmd/importfoods --dry-run --file ../../docs/data/new-foods-2026-10-20.json
```

Output on 20/10/2026 (run without `DATABASE_URL`; a dry run never opens the database):

```
=== H1T MICRO Food Catalog Importer ===
Mode: DRY RUN (No database changes will be saved)
Loaded 6 food records from ../../docs/data/new-foods-2026-10-20.json
Completeness Report: 98.5% average coverage of the 22 counted nutrients across 6 foods
```

Then the real import (upsert on `source` + `source_id`, so a re-run is safe; portions are replaced per food):

```bash
go run ./cmd/importfoods --file ../../docs/data/new-foods-2026-10-20.json
```

## On the VPS (what worked on 21/10/2026)

The commands above assume Go and a current Postgres client on the machine. The VPS (`ssh deploy@14.225.210.185`, repo in `/var/www/nutrition-meals`) has no Go, and its `pg_dump` is 16 while the database is 17, so everything runs in throw-away containers with `--network host`, with `DATABASE_URL` taken from `deploy/.env.prod` and passed as `-e DATABASE_URL` (no value on the command line). The full walk-through, with the dump, the check and the rollback, is `docs/data/new-foods-2026-10-21-import.md`.

Dump first (`postgres:17-alpine`, same server version as the database):

```bash
ssh deploy@14.225.210.185
cd /var/www/nutrition-meals
export DATABASE_URL="$(grep -E '^DATABASE_URL=' deploy/.env.prod | cut -d= -f2- | tr -d '"')"
mkdir -p ~/backups
docker run --rm --network host -e DATABASE_URL postgres:17-alpine sh -c \
  'pg_dump "$DATABASE_URL" --data-only --column-inserts --no-owner --no-acl --table=nutrition.foods --table=nutrition.food_portions' \
  | gzip -9 > ~/backups/foods-before-$(date +%Y%m%d).sql.gz
```

Dry run, then the import (the file is read from the checkout, so it must be on the branch the server has checked out):

```bash
ssh deploy@14.225.210.185
cd /var/www/nutrition-meals
export DATABASE_URL="$(grep -E '^DATABASE_URL=' deploy/.env.prod | cut -d= -f2- | tr -d '"')"
docker run --rm --network host -e DATABASE_URL -v "$PWD":/src -w /src/apps/api \
  golang:1.24-alpine go run ./cmd/importfoods --dry-run --file /src/docs/data/new-foods-2026-10-20.json
```
